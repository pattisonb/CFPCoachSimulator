# CFP Coach Simulator: house rules for anyone editing this repo

## Copy and casing (the player's standing rules)
- **Titles, labels, tags, kickers, tab names, column headers, stat labels, chips and button labels are Title Case**: "Your Offer", "His List", "Blue Blood", "Tier 1", "Sim to Signing Day", "Advance to Keep Them Home", "DC Likes Him", "Not Offered". Never sentence case in those places ("Blue blood", "Not offered", "your 135" are wrong). Small words (a, an, the, of, to, for, and, or, in, on, at, by) stay lowercase inside a title unless first or last.
- **Sentences** (help text, toasts, scene lines, History lines, reasons) are ordinary sentences: capital first letter, a period, sentence case otherwise.
- **A value that starts with a word starts with a capital** ("He wants 105", not "wants 105").
- **American spelling everywhere** (favorite, color, defense, center).
- No numbers out of 100 for moods or chances where the game uses words; no "null"/"undefined"/"NaN" ever reaches the page.

## Engine
- The game is JavaScript throughout: `engine_js/` (the play-by-play engine and the runtime: `pyrt.js`, `pystat.js`, `files.js`, `modules.js`), `sim_js/` (the season), `teamdata_js/` (ratings, the team builder), `career_js/` (recruiting, the offseason, the career), `app_js/` (`api.js` the API, `game.js` the whole game for a host). It was ported from Python file for file and keeps Python's names, numbers and dict order; `engine_js/PORTING.md` says why and holds the rules for working in it. No Python comes back.
- The same seed gives the same game, and an old save must still load. Random numbers come from `Random` in `pyrt.js`, never `Math.random`; rounding is `round` from `pyrt.js`, never `Math.round`; a dict with number-like keys that is walked is an `odict`.
- `node tests/test_sim_golden.mjs` must stay byte-identical unless the change is to the season sim itself and the player agreed; recruiting reads, flags and scenes are never in the digest.
- New randomness goes into its own seeded stream (`_rng(state, "<name>")` or ``new Random(`<name>-${seed}-...`)``) appended after existing draws.
- Constants the player may want to tune are module-level, marked `*tune*`, with a one-line comment.

## Front end
- The app is `ui/` (React, Vite, TypeScript); the old `web/` UI is gone. `ui/PLAN.md` holds its design rules and its changelog (newest first): add a row with every change.
- Use the tokens in `ui/src/globals.css` and px spacing; a component is a folder with `index.tsx`, `index.css` and, when it has words, `messages.ts`. Reuse an existing component before making one; anything new is reusable.
- The gate is `npx tsc --noEmit`, `npx stylelint "src/**/*.css"` and `npx prettier --check --end-of-line auto src` in `ui/`. There are no browser tests: look at a change in the browser.
- Words only ever sit on a team color with its `--team-on` (black or white, whichever reads).
- **Containers side by side are the same height** (the player's standing rule): two panels or columns that share a row end on one line, the shorter one stretched to match (`align-items: stretch`, its last panel taking the difference), never a ragged foot.

## Published site
- Vercel builds `main` with `node tools/build_site.mjs --generic` (vercel.json): the app in `ui/` plus the game to run in the browser (`ui/public/worker.js` hosts it, `ui/src/gameClient.ts` calls it; the game ships as one script, `game.js`, and its data as one download, `game-data.br`/`.gz`). `npm run dev` runs the same worker with no server and keeps the real rosters. Saves are in the browser (IndexedDB). A week's games are shared with helper workers (`ui/public/sim-worker.js`) over shared memory, which needs the two cross-origin isolation headers in `vercel.json`: anything the page loads from another origin must allow it (CORS or `Cross-Origin-Resource-Policy`).
- Nothing published carries a real name, with one exception the player chose: a school named for its state or city goes by that place (Alabama, Texas, Houston: `PLACES` in `tools/generic/tables.mjs`), its mascot, stadium and full name still swapped. `tools/generic/tables.mjs` holds the lookalikes (schools, mascots, bowls, conferences, trophies, awards) and `tools/generic/scrub.mjs` draws same-initial names for players and coaches. A new real name in the data or in the game's words needs a lookalike there; `node tests/test_generic_names.mjs` is the gate.
- **Skins**: a player can load one file on the published site (Load a Skin on the first screen) to see other names and rosters in his own browser; `node tools/make_skin.mjs` makes the one with the repository's own. **A skin is never committed and never part of a build** (it holds the names the site must not carry: `skins/` and `*.skin.json*` are git-ignored). The generic build publishes only where names stand in its scripts (`game.names.json`, `app.names.json`: places and marks, no names) and `ui/public/skin.js`, which writes a skin's names there as plain text and nowhere else; a skin carries its rosters as the game reads them, and the browser makes only the base league from them. `node tests/test_skin.mjs` is the gate (a skin cannot run code, the build holds none, and the skin gives the source build's data and career exactly); `node tools/skin_compare.mjs` is the same in a browser. A change to what a skin must hold raises `FORMAT` in `skin.js`. README "Skins" has the rest.
- The preset faces (`cfb_sim_data/faces/`) are published: only who a face belongs to is a name, so the scrub renames those keys and the file and never touches the face parts.
- Branches: `main` is the React app; `v0` (the old `web/` site), `v1` (Clear Mode before React), `v2` (the React app with the old rosters and ratings: before the 70-average scale, the real-player rosters and the preset faces) and `v3` (the last version with the game in Python) are kept as they were.

## Process
- Tests are plain scripts: `node tests/<file>.mjs`; the full suite is `node tests/run_all.mjs`. Keep testing light: run the tests that touch what changed, not the full suite, unless the player asks.
- `npm run dev` picks up a change to the game's code on its own (the page reloads); a change to the game's data needs it restarted.
- **The rosters the game reads are static files in the repository, and they are the rosters** (the player's rule: change a rating there and it is the rating): `data/engine_teams.json` and `data/player_potential.json`, committed. Nothing makes them: not the game, not `npm run dev`, not a build of the site (a generic build swaps the names in its copy), and a skin carries its own. The hand ratings and the real-usage depth charts that once went into making them are part of them now (`data/manual_ratings.json` is gone; `data/real_adjustments.json` keeps only the usage the live game reads). A career's league takes every real player's ratings from the roster file (`league._roster_ratings`), so a rating changed there carries into every season. **Each player has one labeled set of ratings there and nothing worked out** (`"ratings": {"speed": 96, "catching": 97, ...}`: the 54 of `game_scale.keys()`, 1-99 **on the scale the game shows**, the average player about a 70: the number in the file is the number on his card). A player is one line of the file. Everything else about how good he is (the numbers the play engine reads, his card's `attributes`, `ovr`, `ratings_at`, his stored `skills`) is worked out from that set when the file is read (`teamdata_js/rosters.js`), so a rating changed by hand is his rating everywhere, season one included. **A rating change is an edit to that line and nothing else**: never a script, a corrections file, a build step or a worked-out number stored beside it. His team's depth chart (`role`, `depth`, `in_game`), tendencies, coaches and `level_shift` are stored as they are. `node tests/test_static_rosters.mjs` and `tests/test_roster_source.mjs` are the gates.
- A quick change to the app alone (`ui/`: wording, layout, a component; nothing in the game's folders, the build or the data) goes straight to `main` once the front-end gate passes, with no wider test run (the player's standing rule). Anything that touches the game waits for the tests that cover it.
- Commits end with the session's two attribution trailer lines; no model identifiers in code or commits.
